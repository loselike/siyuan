## 2. 业务主线和生命周期

### 2.1 Sunny 总业务定位

Sunny 是跨境货代内部运营系统，不是普通订单管理，也不是单纯把 Excel 搬到网页上。它要解决的是客户、仓库、业务员、排货、客服、财务在 QQ/微信群、Excel、截图、小本子和不同财务表里重复登记的问题。

当前真实痛点：

- 仓库知道货到了，但业务员要自己去仓库表里找。
- 业务员收了钱、录了单，财务还要翻聊天记录确认水单。
- 排货知道真实代理和真实渠道，但业务员、仓库、客服能看到的信息不同。
- 仓库发没发走，要靠截图或群消息通知。
- 客服不知道货卡在哪个节点，业务也无法按预计时间主动跟进。
- 财务应收、业务成本、真实应付、代理账单、跨越账单和杂费分散在不同表。
- 报价查价要看十几个表，依赖人工记忆、聊天记录和手工复制。

Sunny 的目标是把这些散点变成一条可追踪、可审核、可查账、可分权限的数据链。后续开发不要按“哪个 Excel 页没做”来排，而要先判断这次改动能不能让包裹和费用闭环更顺。

### 2.2 全链路主流程

完整主流程应是：

客户沟通 -> 客户资料建档 -> 业务员给客户仓库地址/客户代码 -> 客户送货或公司安排提货 -> 仓库扫描/导入收货数据 -> 今日收货 -> 在仓数据 -> 理货、拆票、合票 -> 业务员基于仓库货物录单 -> 业务员录应收和业务成本 -> 水单上传/到账审核/匹配订单 -> 业务员提交审核 -> 待审核运单 -> 审核通过进入待排货 -> 排货人员填写真实代理、代理渠道、真实应付 -> 排货审核后进入待出库 -> 仓库打印代理交接单并确认出库 -> 客服数据确认 -> 填转单号 -> 待离港 -> 已离港 -> 已到港 -> 已派送 -> 业务员确认签收 -> 异常进入问题件/售后 -> 财务应收审核、业务成本审核、应付审核 -> 待付款 -> 已付款 -> 代理账单核对/杂费补录/利润统计。

必须互相追溯的核心对象：

- 客户编号：全系统主识别键，客户名称只是辅助展示。
- 仓库包裹：从扫描/导入开始，承载重量、尺寸、件数、异常、拆合票和理货状态。
- 运单号：业务录单后的订单主线，连接仓库货物、费用、排货、客服和财务。
- 转单号：代理或承运商返回的后续物流跟踪主线。
- 费用行：应收、业务成本、应付、杂费都必须能追到具体订单和操作来源。
- 水单：连接客户收款、到账审核、应收匹配和余额归档。
- 代理账单：连接真实应付、待付款、已付款和后续 AI 核对。
- 操作日志：串起每一次拆票、合票、审核、反审核、出库、修改、付款和推送。

### 2.3 两条核心生命线

包裹生命周期：

已收货 -> 在仓 -> 待理货 -> 已理货 -> 已录单 -> 待审核 -> 待排货 -> 已排货 -> 待出库 -> 已出库 -> 数据确认 -> 待转单号 -> 待离港 -> 已离港 -> 已到港 -> 已派送 -> 已签收 -> 售后/归档。

费用生命周期：

录单应收 -> 水单上传 -> 水单到账审核 -> 水单匹配应收 -> 应收审核 -> 业务成本录入 -> 业务成本审核 -> 排货生成真实应付 -> 代理数据确认修正应付 -> 应付审核 -> 待付款 -> 付款申请 -> 已付款 -> 代理账单核对 -> 杂费补录 -> 利润统计/归档。

这两条生命线的关系：

- 包裹没有完成收货/在仓事实，录单就缺少货物数据来源。
- 录单没有生成运单和费用行，排货、应收、业务成本就缺少财务基础。
- 排货没有真实代理/代理渠道/应付，待出库和付款链路就缺少事实来源。
- 出库后没有客服数据确认，转单号和后续轨迹状态就不可靠。
- 水单、应收、业务成本、应付、付款申请和已付款必须围绕同一运单和费用行追溯，不能散在多个互不关联的表。

### 2.4 关键模块补充规则

客户资料：

- 客户编号是主识别字段，仓库条码识别、录单、财务水单匹配都以客户编号为准。
- 客户名称不能作为唯一识别依据，只用于业务员辨认客户。
- 结算方式绑定默认币种，录单时应自动带出。
- 录单填写新收货人信息时，应提示是否保存到客户资料。

基础资料和公司渠道：

- 费用名称要支持运费、报关费、纸箱、胶带、围膜、标签、理货费、提货费、送货费等。
- 代理银行账号应挂在代理资料下，一个代理可保存多个银行账号，当前文本倾向最多 3 个。
- 公司渠道是计费核心，必须支撑业务类型、渠道类别、渠道名称、除材积、多件重量计算方式、单件重量进位规则、结算重量计算规则、结算重量进位规则、大货起始重量和偏远规则。
- 重量进位要能表达类似：21kg 以下按 0.5kg 进位、21kg 以上按 1kg 进位，15.2 -> 15.5，15.7 -> 16，21.1 -> 22。
- 汇率要有当前汇率和历史汇率，历史订单不能因为今天修改汇率而重算；费用合计应按订单录入时间或费用生成时间匹配当时汇率。

仓库：

- 仓库入口来自扫描设备或月度仓库总表；设备抓条码、重量、尺寸、扫描时间。
- 机器默认算 6000 材积，系统还要补算 5000 材积。
- 暂时不接 PDA/设备实时接口也可以，先支持导入、复制或扫描结果进入系统。
- 今日收货是入库作业台，在仓数据是还没出库的库存池；已出库货物默认不显示，但要能筛选出仓/归档历史。
- 拆票不是平均拆，用户要填写拆成几票、每票多少件；原始单号和拆票记录必须写操作日志。
- 合票后原包裹要绑定到新运单，避免重复出货。

录单：

- 录单是业务员把仓库货物转成运单的动作，入口包括在仓数据点“录单”、合票后进入录单、录单页手动选择仓库货物。
- 业务员不想逐件填重量尺寸，应优先从仓库货物自动汇总件数、重量、体积、材积和计费重。
- 业务员通常只确认结算重量、渠道、目的地、费用和内部备注；内部备注可能用于后续财务核对，不能丢。
- 业务员录单时主要看应收和业务成本，不看真实应付、真实代理渠道和真实利润敏感口径。

排货：

- 排货不是简单分配渠道，而是排货人员根据业务员录入的业务成本，选择真实代理、真实代理渠道并填写真实应付。
- 排货字段必须包含运单创建时间、排货时间、站点、业务员、客户编号、运单号、业务渠道、真实代理、真实代理渠道、货物数据、业务成本、业务成本合计、应付成本、应付成本合计、排货人、排货审核人和状态。
- 业务员看业务渠道和业务成本；排货、财务、管理员看真实代理渠道和真实应付；仓库不需要看价格，只需要看代理、渠道和交接单信息。
- 排货时间是关键字段，用于判断排了几天还没出库。

客服：

- 客服状态不是一个简单状态字段，而是一组状态池：待离港、已离港、已到港、已派送、已签收、售后。
- 每个状态池应支持当前状态列表、批量操作、单票确认进入下一状态、修改预计时间、上传附件、填备注、选择是否推送、选择是否显示追踪网站、挂问题件和查看停留时长。
- 转单号前必须完成业务数据和代理数据双审核。
- 追踪网站默认对业务员隐藏，勾选后业务员可见。
- 已离港要维护预计到港时间，并支持按预计到港时间排序；延误时可修改预计到港时间。
- 已签收最后由业务员确认更合理；异常签收进入售后。
- 问题件不能把订单从原状态池移走；订单仍留在原状态池，同时在问题件中心汇总。

财务：

- 应收来自业务录单和单个订单费用界面，水单必须同客户、同币种，匹配金额不能超过余额。
- 已到账水单才应允许正式匹配；应收反审核要检查是否已有水单匹配。
- 业务成本是公司内部给业务员核算利润的成本，不一定等于真实应付；应收 - 业务成本 = 业务利润。
- 应付是真实付给代理或供应商的钱，业务员默认不可见；应付审核后生成待付款。
- 已生成待付款后不能随便反审核，已付款后必须走撤销付款链路。
- 待付款最好按代理 + 银行账号 + 币种分组，跨代理、跨银行、跨币种不能混在一张付款申请里。
- 付款凭证必须能回查到待付款、应付费用和运单。
- 杂费、提货费、送货费、货拉拉、跨越、物流专线、仓库统计的其他杂费未来都要能进入业务成本或应付；第一阶段先保留为单票费用新增费用行，后续再做批量导入和匹配。

### 2.5 最容易漏的关键点

- 待出库要有排货时间。
- 仓库不能看价格。
- 业务员不能看真实应付和真实代理渠道。
- 转单号前必须完成业务数据和代理数据双审核。
- 问题件不能把订单从原状态池移走。
- 追踪网站默认对业务员隐藏。
- 代理银行账号挂代理资料。
- 汇率必须按历史时间匹配，不能改当前汇率影响老订单。
- 杂费未来要能进入业务成本和应付，不要把费用模型设计死。
- 业务员确认签收是最后节点，不是客服全包。
- 录单不要逼业务员逐件填尺寸重量，要从仓库货物汇总。
- 发票模板应该跟代理/渠道绑定，排货后业务员可下载。
- 代理账单 AI 核对、AI 价格表识别、PDA 实时接口、企业微信真实推送都应后置，先把基础闭环跑顺。

### 2.6 业务主闭环

Sunny 要解决的不是单点录单，而是把原先分散在 QQ/微信群、Excel、仓库机器表、财务表里的动作串成一个闭环：

1. 基础资料先建好：客户编号、客户名称、业务员归属、结算方式、收货人信息、代理资料、代理渠道、公司渠道、汇率、用户组、站点和权限。
2. 仓库收货先进入系统：仓库扫描外部标签，系统不生成入库标签，但要识别 `客户单号-快递单号`，自动拆出客户编号和快递号，匹配业务员和站点。
3. 在仓数据承接所有未出库货物：业务员只能看自己的，仓库看全部。异常只做提醒，不要求解决闭环；异常内容 hover 或弹窗显示，避免挤占表格。
4. 理货支持需求、拆票、合票：理货要求从在仓数据进入未完成理货；完成后生成理货后标签，保留原始数据和原客户单号到操作日志。
5. 合票或选择仓库货物进入录单：录单要自动带客户编号、客户名称、仓库货物数据、业务渠道、目的地、货物类型、报关、敏感、收货人和费用。
6. 业务员录单并提交审核：业务员填写应收和业务成本；应付对业务员隐藏。待审核顶部要自动生成固定格式摘要，审核后进入待排货。
7. 市场排货：市场根据业务员成本和真实代理/代理渠道选择实际出货方案，补应付成本，确认后审核进入待出库。待出库必须显示排货时间，便于追踪安排了几天未出。
8. 仓库出库：仓库按待出库勾选打印代理交接单，批量已出库。出库后仓库主流程结束，进入客服数据确认。
9. 客服数据确认：业务数据和代理数据要分别审核、修改、反审核。两个数据都审核后才能进转单号。代理返回计费重和业务计费重不一致时，要能反馈业务员确认。
10. 客服转单号和轨迹节点：填写转单号、上传面单、按需推送业务员、按需展示追踪网站。之后进入待离港、已离港、已到港、已派送、已签收。
11. 问题件横跨状态：问题件既进入问题件集合，也保留在原状态池中；要记录问题停留时间，支持人工填写问题原因和常用原因。
12. 财务应收、业务成本、应付三条账：三类费用都来自订单事实，单个订单费用界面和总表双向同步，审核后锁定，反审核按权限开放。
13. 水单匹配：业务员/财务上传水单，水单编号自动生成；到账后才能匹配还是录入后可匹配需最终确认，但当前开发应保留状态限制能力。水单余额为 0 且应收审核完毕后自动归档。
14. 待付款和已付款：应付审核后进入待付款，选择代理银行和上传供应商账单截图；付款后记录付款方银行、付款日期和付款水单，进入已付款核销。
15. 代理账单核对：后续导入代理账单，用 AI 自动核对系统应付、代理账单、付款申请和已付款。
16. 操作日志贯穿全流程：拆票、合票、理货完成、排货审核、出库、数据确认、转单号、财务审核/反审核、付款、水单匹配都要写日志。

### 2.7 口头文本重点

这些规则主要来自沟通文本，Excel 只提供字段补充。后续开发不能漏：

- 客户编号是主识别键，客户名称只是帮助业务员识别客户；仓库、录单、财务、水单匹配都应优先按客户编号流转。
- 结算方式和币种绑定，客户资料里维护后，录单时不应让业务员重复判断币种。
- 收货人资料最多四组，可在客户资料提前维护，也可在录单时保存，下次同客户发货直接勾选。
- 代理发票模板要在代理资料里上传，后续按代理/渠道匹配，自动填入客户、货物、收货人等字段后下载，剩余字段由业务员补。
- 仓库外部标签已经由小程序生成，Sunny 不负责生成该入库标签，只负责识别扫描数据并自动匹配客户编号、业务员和站点。
- 仓库机器数据目前来自固定格式表格或扫描结果，PDA/设备实时接口不是第一阶段必须项；先保证数据能进入今日收货和在仓数据。
- 聊天文本里的“收货”指仓库扫描/导入包裹进入今日收货和在仓数据，不是运单上的 `receiveShipment` 状态接口；验收“货从收货到出库”必须以仓库包裹生命周期为准。
- 仓库件数允许人工修正，因为同规格多件货不会逐件过机；原始扫描数据和人工修改都应留痕。
- 异常只是提醒，不要求“处理完成”闭环；异常内容不要直接铺满表格，应 hover 或弹窗查看。
- 拆票只在同票同数据货物上做，拆出来的编号追加 `-1/-2/-3`，继续拆时编号继续递增；合票后进入录单。
- 货物出库后不能从系统消失，应从默认在仓视图移出，同时保留归档/出库数据查询。
- 业务员录单时主要填写应收和业务成本，应付是真实付给代理的成本，业务员不可见。
- 业务员审核后进入待排货；市场排货先确认代理/代理渠道/应付成本，再审核进入待出库。
- 待出库必须增加排货时间，用来判断市场已安排但仓库几天未出的问题。
- 数据确认是客服动作，业务数据和代理数据分别审核；代理返回计费重高于业务数据时，要能反馈业务员确认差异。
- 转单号确认后进入待离港；面单上传、是否推送、追踪网站是否对业务员显示都由客服控制。
- 轨迹节点要让客服和业务知道货现在卡在哪个环节，不能继续依赖聊天记录。
- 问题件要既出现在问题件集合，也保留在原业务状态池；要能看问题停留时长，优先处理滞留久的单。
- 已签收最后可由业务员确认；售后问题也归入问题件/售后筛选。
- 水单付款编号不能重复；水单到账状态影响能否匹配订单的最终规则需要保留配置/权限空间。
- 付款给代理时，代理银行账号挂在代理名下，可手填并选择是否保存，最多三组是当前文本倾向。
- 跨越、货拉拉、提货费、仓库杂费、代理账单等后续成本来源都应最终进入单个订单成本，但第一阶段先不展开复杂导入。
- 报价/查价未来希望从多表查价转到系统查价，但必须先把基础业务闭环跑顺。
