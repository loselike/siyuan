# 仓库理货事实一致性与历史验数

## 1. 业务目标
确保“已理货”只来自完成的理货任务，录单、清理测试数据或历史残留不能制造虚假理货标识。

## 2. 使用角色
仓库可创建/完成理货并查看历史；市场、客服只读理货结果；业务员和财务不能修改理货事实。

## 3. 用户流程
仓库从在仓数据发起理货→进入未完成理货→完成后从未完成消失并进入近一月/历史；点击“理”可追到任务、组合号、包裹和操作人。异常关联显示修复提示而非伪造状态。

## 4. 业务规则
- `tallyTaskId + tallyTaskNo + COMPLETED/已理货` 同时成立才显示“理”。
- 完成操作幂等；已完成任务不能再次完成或修改需求。
- 删除/清理测试任务不得留下包裹孤儿关联。
- 历史修复先只读扫描，任何批量回填需独立授权和脚本审计。

## 5. 不做范围
不自动修改线上历史数据；不重做仓库模型；不改变排货/出库状态。

## 6. 工程落地点
WarehousePage、WarehousePackage/TallyTask 查询与约束、Prisma/内存仓储一致性、仓库 E2E、只读诊断脚本或报告。

## 7. 验收标准
- 未理货包裹永不显示“理”，录单后也不改变。
- 完成理货后未完成池消失、历史池出现且关联可追溯。
- 构造孤儿关联时页面不误判并有可定位错误。
- Prisma 与内存仓储相同样本返回一致。

## 8. 验证命令
```bash
npm test -w @siyuan/web -- --run src/modules/warehouse/warehouse.test.tsx -t "理货|历史|未完成"
USE_PRISMA_REPOSITORY=false npm test -w @siyuan/api -- --run src/modules/app.warehouse.e2e.test.ts -t "tally|理货"
npm run typecheck -w @siyuan/api && npm run typecheck -w @siyuan/web
```

## 9. 风险与待确认
历史线上脏数据的修复策略需要先输出只读数量和样本，再由用户授权。
