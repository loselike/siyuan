# 任务卡通过标准

正式任务卡进入代码会话前，必须满足以下标准。任务卡不是代码执行的唯一形式；用户在当前会话明确授权且范围清楚时，可按下方“非任务卡直接执行”规则开工。

## 必须通过

- **业务目标清楚**：能一句话说清楚这张卡解决什么问题。
- **角色清楚**：明确谁能看、谁能操作、谁不能操作。
- **流程清楚**：入口、操作、结果完整，不只写“优化某模块”。
- **规则清楚**：状态、费用、权限、字段显隐至少覆盖本卡涉及部分。
- **边界清楚**：明确本卡不做什么，避免扩成全系统改造。
- **验收可测**：至少有 3 条可验证标准。
- **工程范围可控**：能判断大致影响 API、Web、Shared、Prisma 哪些层。
- **没有阻塞问题**：如果还有业务方向未确认，不能进入代码落地。
- **验证命令明确**：至少包含当前模块小验证命令。
- **可独立交付**：完成这张卡后，即使后续卡未做，系统也不应处于半残状态。

## 会话准入

- 规划会话只读代码和文档，输出 `docs/tasks/YYYY-MM-DD-模块-业务动作.md`。
- 代码会话一次只执行一张已通过标准的任务卡，或一个用户明确授权的非任务卡需求，并从 `docs/dev-now/_template.md` 创建自己唯一的 `docs/dev-now/<session-slug>.md`。
- `docs/dev-now.md` 是只读索引；代码会话不得自动修改，也不得修改其他会话的独立状态文件。
- 同一任务卡只能有一个 `in_progress` 状态文件；并发开发优先使用独立 worktree 和独立 `codex/<session-slug>` 分支。
- 发布会话只负责 47 同步、构建、迁移和健康检查。
- 审查会话只输出风险清单和修复建议，不直接改业务代码。

## 非任务卡直接执行

满足以下条件时，不要求先创建 `docs/tasks/*.md`：

- 用户在当前会话明确要求修改、修复、实现、落地或执行。
- 业务目标和期望结果清楚，代码会话无需猜测关键口径。
- 修改范围可控，能够判断相关 Web、API、Shared、Prisma 或文档边界。
- 至少能确定一个最小相关验证；风险较高时按实际影响扩大验证。
- 不存在尚未确认的不可逆数据、线上发布、付款、权限模型或数据库结构方向。

非任务卡执行时，独立会话状态文件必须记录输入摘要、允许修改范围、不做范围和验证结果。若上述条件不满足，先向用户确认，不强制补任务卡，但不得边猜边实现。

## 命名规则

正式任务卡命名为：

```text
YYYY-MM-DD-模块-业务动作.md
```

示例：

```text
2026-07-07-warehouse-receive-flow.md
2026-07-07-finance-payable-review.md
```

## 不通过示例

- 只有“优化财务页面”，没有角色、流程和验收标准。
- 只有接口列表，没有业务目标和用户流程。
- 写了“全系统统一调整”，但没有拆成独立可交付卡。
- 存在未确认的财务、权限或状态流转问题，却要求直接落代码。
