# Sunny 开发会话详细规则

本文档承接 `AGENTS.md` 中不适合每次默认展开的细则。需要做多会话协作、长需求拆卡、模块大改、前端布局治理或验证策略时读取本文档。

## 多会话协作

后续需求优先从业务视角管理：复杂需求可先由规划会话产出任务卡，再由代码会话按卡落地；用户也可以在代码会话中直接明确要求实施。会话按以下优先级分工，避免多个会话同时改共享文件：

1. 规划会话：按一个模块或一个业务主题只读分析，输出 `docs/tasks/YYYY-MM-DD-模块-业务动作.md`；不改业务代码。
2. 代码主会话：一次只执行一张已通过的任务卡，或一个用户明确授权且范围清楚的非任务卡需求；只维护自己认领的 `docs/dev-now/<session-slug>.md`。
3. 发布会话：只负责 47 同步、Docker 发布、迁移和健康检查；不顺手改业务代码。
4. 审查会话：只输出风险清单、验收问题和修复建议；不直接改业务代码。
5. UI 人工验收由用户在 47 页面完成；Codex 只输出页面入口、变更区域和人工检查点，不创建浏览器调试会话。
6. UI 落地会话：根据已确认任务卡或 UI 调试结论做前端落地；能复用就复用，系统确实没有能力时才补接口或逻辑。

共享高风险文件包括 `.codex-state.md`、Prisma schema/migrations、RBAC、`packages/shared`、全局样式、共享表格组件、`App.tsx`、包管理文件和发布脚本。改这些文件前必须说明影响面，并确认没有其他会话正在处理同一区域。

多代码会话并发规则：

- `docs/dev-now.md` 是只读索引，任何代码会话都不得自动改写。
- 每个代码会话必须认领唯一的 `docs/dev-now/<session-slug>.md`，例如 `quote-pricing-oversize.md`、`master-data-agent.md`、`finance-water-receipt.md`。
- 会话只能修改自己认领的状态文件，不得删除、覆盖、归档或重建其他会话的状态文件。
- 每个会话状态文件只记录一个输入来源：一张 `docs/tasks/*.md`，或一个当前会话中的明确实施请求；不得混入第二个需求。
- 如果某任务卡已有状态为 `in_progress` 的会话文件，其他会话不得重复认领；需要接手时先由用户或主推进会话把原状态改为 `handed_off`。
- `.codex-state.md` 不承担抢锁、占位或当前任务指针；代码会话完成时先更新自己的状态文件，只由主推进会话或用户明确授权的会话追加高信号完成记录。
- 并发修改代码时必须为每个会话创建独立 worktree 和 `codex/<session-slug>` 分支。仅在同一工作目录切换不同分支仍会共享未提交文件，不属于并发隔离。
- 无法使用独立 worktree 时，多个会话必须按文件所有权完全分区；一旦修改文件或同一业务调用链重叠，只保留一个写会话，其他会话改为只读审查或等待。
- 多会话只允许并行开发和本地验证；47 发布使用单一全局队列。每个完成会话记录候选 commit/白名单、文件清单、测试证据和发布范围，发布协调会话串行合并或逐个发布。
- 发布锁必须覆盖远端基线读取、同步/CAS 条件上传、Docker 构建、迁移、重启、健康检查和状态写入；锁被占用时排队，禁止任何会话锁外 `scp`、`sync:47 --apply` 或远端 Docker 操作。
- 标准全树发布仅允许发布协调 worktree 使用；`release:47:baseline` 会先确认该 clean worktree 与 47 实际 manifest 一致，再把线上 ID 绑定当前 worktree、分支和祖先 commit。其他会话已推进 baseline 或 receipt 不匹配时，旧候选先合并/重验，不得以发布时刚读取的新 baseline 绕过。
- 发布在源码修改后失败时，远端 recovery-required 标记会阻断全局队列；主推进会话必须依据备份、容器、迁移和 health 证据恢复后，按 marker checksum 显式清除，不得由后续会话直接抢锁覆盖。

### 业务视角任务卡

- 正式任务卡放在 `docs/tasks/`，命名为 `YYYY-MM-DD-模块-业务动作.md`。
- 任务卡必须基于 `docs/tasks/_template.md`，并通过 `docs/tasks/_acceptance.md` 后才允许进入代码会话。
- 规划会话优先写业务目标、角色、用户流程、业务规则、不做范围和验收标准；工程落地点只写必要边界。
- 代码会话不重新发散需求；如果任务卡缺少关键业务决策，回到规划会话补齐。
- `docs/dev-now/<session-slug>.md` 只记录该代码会话正在落地的一张任务卡、状态、分支/worktree、允许改动范围和验证结果，不承载其他需求。
- `docs/dev-now.md` 只保留索引规则，不维护动态任务清单，避免它再次成为共享写热点。
- `.codex-state.md` 只追加高信号完成记录和验证结论，不记录讨论过程，也不作为并发锁。

### 非任务卡直接执行

- 用户明确说“修改、修复、实现、落地、执行”并给出足够上下文时，视为代码修改授权，不要求先补 `docs/tasks/*.md`。
- 非任务卡输入可以是当前会话中的文字要求、截图标注、已确认计划或明确文件范围。
- 开工前仍需确认：目标可一句话说明、修改范围可控、不做范围可从请求判断、至少能运行一个最小相关验证。
- 状态文件中的“输入来源”写为 `无（当前会话明确请求）`，并在“输入摘要”记录本轮目标、边界和验证命令。
- 如果缺少关键业务决策，或涉及不可逆数据、线上发布、付款、权限模型、数据库结构等高风险方向，仍按 `Ask User Only When` 暂停确认。
- “允许非任务卡”不允许代码会话从 `.codex-state.md`、其他会话状态或旧聊天记录自行挑选任务开工。

### 任务卡进入代码会话的门槛

- 能一句话说明业务目标。
- 明确角色、入口、操作、结果、权限和字段边界。
- 明确不做范围，避免扩成全系统改造。
- 至少有 3 条可验证验收标准。
- 至少有当前模块小验证命令。
- 没有未确认的高风险财务、权限、状态流转或发布问题。

## Ponytail Development Discipline

本项目默认采用 Ponytail 风格作为常驻开发纪律：少写代码、少加依赖、少造抽象，优先交付最小正确闭环。该纪律用于控制复杂度，不能覆盖安全、权限、财务一致性、数据完整性、测试验证和用户明确需求。

- 先复用现有模块、类型、API、样式和测试，再考虑新增文件或新抽象。
- 优先使用 TypeScript/Node/浏览器平台能力和仓库已有依赖；新增依赖前必须说明为什么现有能力不足。
- 每次改动尽量靠近需求涉及的模块；禁止顺手重构无关代码、批量格式化无关文件或改动无关业务流程。
- 新抽象只有在减少真实重复、降低共享复杂度或符合现有模块边界时才允许添加。
- 能删掉旧分支、旧 fallback、重复 UI、重复映射或无用 helper 时，优先删除；但删除前必须确认没有测试、路由、页面或线上兼容依赖。
- 对临时简化方案，用 `ponytail:` 注释写明边界和后续触发条件。

## 最低修改与复用优先规则

每次开发前先做复用检查，避免为了新入口重复造接口、重复造组件或复制业务逻辑：

- 是否已有相同业务入口，或已有页面、弹窗、抽屉、详情面板可以扩展。
- 是否已有 API、DTO、查询参数、状态字段或共享类型可以承载本次需求。
- 是否已有数据库字段或持久化位置可以表达该业务含义。
- 是否已有权限判断、字段裁剪、菜单入口、数据范围和操作日志可以复用。
- 是否已有测试样本、测试桩或验收命令可以扩展。

开发顺序固定为：

1. 先复用现有 UI 入口。
2. 再补齐现有组件字段和状态。
3. 再复用现有接口返回必要字段。
4. 再补接口参数或响应裁剪。
5. 最后才新增接口、数据库字段或新组件。

禁止做法：

- 没检查现有接口就新增接口。
- 没检查现有组件就新建重复弹窗。
- 为一个页面复制一套相似后端查询。
- 前端隐藏敏感字段但后端仍返回全量敏感数据。
- UI 重构时顺手改变业务流转、权限模型、数据库结构或线上数据。
- 本地最小验证未通过、候选文件边界不清或混有其他任务改动时直接发布到 47。

只有满足以下条件之一，才允许新增接口、字段、组件或后端逻辑：

- 文本需求或 Excel 字段存在真实业务字段，当前能力没有承载位置。
- 当前接口无法保证敏感字段以后端方式裁剪。
- 当前状态流转缺失，复用会造成错误业务闭环。
- 当前日志无法追溯审核、反审、付款、作废、转单号、出库等关键动作。
- 当前组件无法表达必要业务结构，例如多费用行、水单匹配、标签预览或代理账单核对。
- 复用会造成越权、财务口径错误、重复提交或数据追溯断裂。

处理既有代码时：

- 普通功能开发不触发旧代码审计；只按本次需求做最小相关改动。
- 只有用户明确要求重构、瘦身、整理旧代码、降低复杂度，或当前文件继续堆叠会明显增加风险时，才先审计再改动。
- 审计时先列出重复、过度封装、无用依赖、大文件堆积和可合并逻辑，不一次性全项目重构。
- 业务大文件拆分只沿现有领域边界推进，例如 finance、warehouse、orders、routing；禁止为了“看起来更架构化”新增无业务价值的层。

## Long Requirement Protocol

用户贴长 PRD、截图拆解、阶段计划或详细字段清单时，不要把整份文档当成一次性实现范围。先压缩成一张短执行卡片：

```md
目标：
本次阶段：
涉及模块：
必须做：
不要做：
验收标准：
最小验证：
```

处理规则：

- 如果文档包含多阶段计划，默认只执行第一阶段或用户明确指定的阶段。
- 只读取与本次阶段相关的代码；不要因为文档同时提到 API、数据库、权限、UI、发布就全部展开。
- 每次实现必须控制在一个可验证闭环，优先复用现有接口、类型、测试和页面结构。
- 大功能优先落地“展示/读取”或“单类 CRUD”，再做批量操作、权限矩阵、列设置、通知、导入导出等增强。
- 同一轮不要同时做多阶段功能、47 发布、巨型模块重构、数据库大迁移；除非用户明确要求。

## GPT-5.6 Agent Routing Details

### Operating Model

- 项目主线程固定为 `gpt-5.6-sol` High。它负责理解用户目标、读取真实仓库状态、判断风险、决定是否委派、划定文件所有权、处理升级、整合结果和最终验收。
- 子代理是固定的“模型 + 推理等级 + 职责 + 权限”组合，不允许执行中临时改模型。项目级配置位于 `.codex/config.toml` 和 `.codex/agents/*.toml`，从而避免全局默认模型或未来默认路由变化影响 Sunny。
- 推理等级不等于权限等级。Luna/Terra 可以调查或实施边界明确的任务，但不能独立决定权限、数据库、财务、公共契约、生产或不可逆操作。
- 所有任务都要经过路由判断，但不要求都委派。`NO_DELEGATION` 是正常且优先检查的结果。

### Route Decision

路由前先按真实代码回答五个问题：

1. 当前范围和入口是否已经明确？
2. 预期修改是前端、后端、共享契约、数据库、生产状态，还是只读调查？
3. 是否命中高风险触发器？
4. 验证是否能由一条 focused command 闭环，还是需要独立证据？
5. 委派或并行能否减少主线程噪声/等待，收益是否高于上下文交接成本？

内部记录统一使用：

```md
ROUTE_DECISION
- result: NO_DELEGATION | sunny_mapper | sunny_frontend | sunny_backend | sunny_verifier | sunny_reviewer | sunny_risk_reviewer
- reason:
- risk: low | medium | high
- model_effort:
- validation:
- review:
```

只有发生委派、升级或用户询问路由时才需要在最终回复中说明该记录，避免给小任务增加过程噪声。

### Fixed Roles

- `NO_DELEGATION`：范围和位置已知、无高风险面、改动很小、主线程已有上下文且一次 focused validation 可闭环。典型：文案、明确值、局部样式、字段显隐、单个测试断言、读取一个已知文件。
- `sunny_mapper`：Luna Medium，只读。用于陌生模块地图、大范围跨文件定位、依赖/调用链梳理、长日志归纳和并行证据收集；不做最终根因、安全或业务结论。简单查找由主线程直接 `rg`，不为使用 Luna 而委派。
- `sunny_frontend`：Terra Medium，可写。用于方案已明确的 React/AntD 页面、表格、弹窗、状态与交互实施；不得自行改变 API、权限、财务或数据库。
- `sunny_backend`：Terra High，可写。用于 Sol 已明确不变量、风险边界和文件范围的 API、DTO、Repository、服务端状态处理或查询实现；高推理强度不赋予高风险决策权。
- `sunny_verifier`：Terra Medium，验证专用。顺序执行安全测试、类型检查、构建、47 只读接口、容器、日志或代码指纹证据；可生成工具必需产物，但不得修改源码或自动修复。
- `sunny_reviewer`：Sol High，只读。对完成后的 diff 做独立正确性、回归、兼容、并发/幂等和测试缺口审查。
- `sunny_risk_reviewer`：Sol XHigh，只读。对鉴权、权限、数据库、财务、敏感数据、公共契约、核心状态机、删除/上传、47 和不可逆操作做独立风险审查。

不配置 Luna Low 和 Terra Low：Sunny 中真正极小的定位与修改由主线程直接完成，额外代理的上下文交接通常比模型节省更贵。不配置 Sol 架构实施子代理：架构与复杂根因分析由 Sol 主线程承担，保留 Reviewer/Risk Reviewer 作为独立第二视角。

### Risk Ownership

下列任一项出现时，Sol 主线程必须亲自确认业务事实、授权边界和最小正确闭环：

- Auth、JWT、登录、RBAC、菜单与操作权限、租户或对象归属、数据范围、字段裁剪。
- Prisma schema、migration、历史数据回填、事务和数据兼容。
- 财务金额、币种、汇率、应收应付、付款、核销、反审、作废和审计。
- 上传、下载、预览、敏感文件、客户/订单/员工隐私字段。
- 公共 API、`packages/shared` 契约、跨模块核心业务状态机。
- 删除、恢复、批量写入、外部通知、47 生产环境、密钥和不可逆操作。

高风险不等于禁止委派实现；只有 Sol 已明确方案、授权文件和验证门后，才可把机械实施交给 `sunny_backend` 或 `sunny_frontend`，随后必须用 `sunny_risk_reviewer` 或由主线程完成等价对抗式审查。

### Assignment And Escalation Contract

每个写任务的委派消息必须包含：

```md
目标：
允许修改：
禁止范围：
已知事实：
验收标准：
安全验证命令：
升级触发器：
```

代理发现真实范围超过最初边界、方案不成立、需要未授权文件或进入新的高风险面时，必须停止扩大修改并返回：

```md
ESCALATE_TO_SOL
- 发现的事实：
- 已执行的操作和改动：
- 尚未处理的内容：
- 超出边界的原因：
- 可能受影响的文件或状态：
```

Sol 收到升级后必须重新读取相关 diff/状态，决定收回主线程、重划范围、改派固定角色或向用户请求必要授权；不得让原代理以“顺便完成”为由继续扩改。

### Concurrency And Handoff

- `.codex/config.toml` 固定 `max_threads = 3`、`max_depth = 1`，只允许主线程直接管理一层子代理。
- 默认同一时刻只有 1 个写代理。`sunny_mapper` 的多个互不依赖只读调查可以并行；`sunny_verifier`、`sunny_reviewer` 和 `sunny_risk_reviewer` 通常在实现完成后顺序运行。
- 两个写任务只有在不同 worktree、不同分支、文件所有权完全不重叠且主线程明确授权时才可并行。共享工作区只切分支不构成隔离。
- 子代理必须知道自己不是唯一操作者：不得还原、覆盖、清理或格式化其他会话改动；主线程验收时必须重新检查 `git status` 和实际 diff。

### Frontend Rule Priority

- Sunny 本地 `frontend-design` 和业务 UI 原则是 UI/UX 最高优先级；`sunny_frontend` 只补 React/AntD、状态管理、组件拆分、性能和可访问性实现。
- 小型文案、局部样式、字段显隐、列宽调整优先 `NO_DELEGATION`。
- 新建页面、二级功能、复杂弹窗、抽屉或表格重构：先明确业务任务、目标岗位、核心字段、布局密度和隐藏入口，再按需调用 `sunny_frontend`。
- UI 字段落地通过组件测试、类型、构建、接口和线上静态产物验证；视觉与排版由用户在 47 人工验收，不需要浏览器验证代理。
- 冲突时以 Sunny 现有设计系统、AntD 用法、业务字段完整性、权限裁剪和可扫读效率为准。

### Routing Evaluation

先运行 2 周或累计 10 个有代表性的任务，再决定是否增加固定角色。样本至少覆盖：小型 UI、常规前端、报价导入/规则、仓库状态流转、财务水单/应收匹配、RBAC 或 migration、47 发布检查。

每个样本记录：路由结果、实际模型/推理等级、总耗时、首轮验证是否通过、返工次数、是否升级、是否发生无效委派或文件冲突。优化目标按优先级排序：事故与越权风险不增加；首轮通过率不下降；主线程上下文噪声明显减少；总耗时和模型消耗下降。若某角色连续产生交接成本、返工或越界升级而无稳定收益，先收紧触发条件，不急于增加更多代理。

```md
| 日期/任务 | 路由结果 | 模型/推理 | 总耗时 | 首轮通过 | 返工 | 升级 | 无效委派/冲突 | 结论 |
| --- | --- | --- | ---: | --- | ---: | --- | --- | --- |
```

禁止规则：

- 禁止默认读取或运行全部代理，禁止按任务名称机械路由。
- 禁止为了“多 Agent”拆分一个主线程可直接闭环的小任务。
- 禁止写代理自行扩展文件所有权、业务范围或权限。
- 禁止并行修改同一文件、同一状态机、同一 API 契约或同一数据库结构。
- 禁止审查代理借题做全仓库重构；只输出 P0/P1/P2 和最小阻断动作。

## First Principles Gate

复杂 bug、跨模块数据流、财务/仓库/权限/发布问题，先做第一性原理检查，再决定怎么改。目标是找到业务和系统层面的根因，而不是只补当前报错或当前页面。

触发场景：

- 同一个问题反复出现，或修复后可能在其他模块复发。
- 涉及订单、仓库、财务、报价、权限、审计、47 发布等跨模块链路。
- 涉及金额、币种、状态流转、字段裁剪、历史数据兼容或线上数据。
- 用户明确要求“从第一性原理出发”。

执行要求：

- 先列当前事实：代码入口、真实数据流、权限边界、状态来源和已验证现象。
- 再列本质问题：系统应该保证什么不变量，当前哪一层破坏了它。
- 再定最小正确闭环：优先复用现有接口、类型、状态和日志，只补能消除根因的最小改动。
- 不做泛泛架构升级，不顺手重构无关模块，不把一次 bugfix 扩成全系统重写。

可复制卡片：

```md
第一性原理检查：
事实：
本质问题：
最小正确闭环：
不做范围：
需要验证：
```

## Adversarial Review Gate

高风险改动、状态流转、权限裁剪、财务口径和 47 发布前，必须做对抗式审查。审查目标是找能造成事故的具体失败路径，不是泛泛挑刺。

触发场景：

- 审核、反审、作废、付款、核销、排货、出库、导入、批量操作和发布上线。
- 财务金额、应收应付、代理成本、利润、币种、汇率和付款状态。
- 角色权限、菜单入口、数据范围、字段裁剪和审计日志。
- 用户明确要求“对抗式审查”“全局审查”或“多 Agent 审查”。

审查维度：

- 恶意用户：越权访问、伪造角色、直接调用接口、重复提交。
- 错误数据：空值、超长文本、重复编号、异常币种、负数金额、未来时间、历史兼容数据。
- 流转堵塞：状态无法推进、推进后下游查不到、回退污染已付款/已归档数据。
- 并发和幂等：重复点击、批量操作部分失败、导入重复、重试造成脏数据。
- 发布风险：迁移顺序、线上密钥、Docker 构建、健康检查、旧数据读写兼容。

输出要求：

- 默认只输出 P0/P1/P2 风险和对应最小阻断动作。
- 不输出泛泛优化建议，不借审查名义做无关重构。
- 默认单 Agent 轻量审查；只有用户明确要求“全局对抗式审查 / 多 Agent 审查”才扩大范围。

可复制卡片：

```md
对抗式审查：
攻击面：
可能事故：
必须阻断：
可延期风险：
最小验证：
```

## Product Priorities

- 财务资料库必须支持真实增删改查，不做静态假页面。
- RMB 统一、币种自动识别、结算方式和费用计算属于跨前后端与数据库的核心能力。
- 订单、客户、财务、仓储、权限相关改动要保持 API、前端状态、数据库字段一致。
- 业务动作尽量可追溯，涉及财务和权限的变更要考虑审计。

## Module Delivery Checklist

新增或大改业务模块时，默认按这张清单交付：

- 先确定模块边界：前端放对应 `apps/web/src/modules/<domain>`，API 放 `apps/api/src/modules`，共享类型放 `packages/shared`；禁止重新把页面逻辑堆回 `App.tsx`。
- 新建前端模块、二级功能、工作台、表单、详情、看板或明显重塑已有页面时，必须读取并遵循 `.agents/skills/frontend-design/SKILL.md`；弹窗、抽屉、行内操作、上传、预览、确认框、字段设置、二级/三级入口和空/错/加载/无权限/禁用状态也属于同一轮设计与验收范围；小型 bugfix、文案修正、字段补显隐或测试修复可复用现有设计，不强制重新做完整设计方案。
- 后端新功能必须优先落在领域子模块里。Controller 只做路由/权限/输入输出，Service 做业务规则，Repository 做持久化。
- API 测试默认按领域拆分，例如 `app.finance.e2e.test.ts`、`app.warehouse.e2e.test.ts`、`app.orders.e2e.test.ts`、`app.pricing.e2e.test.ts`。
- 需求字段必须做“前端表单/展示、共享类型、Prisma 字段或持久化位置、API 输入输出、测试数据”五点对应；暂不落地的字段必须写明原因和后续阶段。
- 后端必须成为业务事实来源；新增字段不能只停留在前端状态或测试桩，跨模块数据要能被后续流程读取。
- 开发前必须把 PRD 字段拆成验收矩阵，逐项标记“已落地 / 已映射 / 延期”。
- 每个新模块交付前必须输出简短“需求落地核对”：已落地字段、已落地流程、后端互通点、延期项和原因。
- 新状态或流程节点必须同时补共享状态、后端状态流转、前端筛选/展示、日志记录和回归测试。
- 涉及审核、反审核、撤销、反核销的模块，必须检查下游流转状态，不能直接回退已付款、已核销、已归档等状态。
- 导出必须按当前完整筛选条件或勾选范围输出，不能只导当前分页或固定前 100 条；后端仍要按权限裁剪字段。
- 上传、粘贴、凭证、水单等入口不能只做视觉按钮；暂未接对象存储时，必须明确保存文件元数据和 URL/路径。
- 列表到详情类页面禁止默认选中第一条数据，除非需求明确要求。
- 前端测试桩必须 mock 新增的真实 API 路径，不允许只依赖本地备用数组或旧接口让测试“看起来能过”。
- 聚合提交接口要在后端事务里完成主表、明细、费用、仓库包裹、审计日志等同步写入；草稿和正式提交的副作用必须分开。
- 涉及角色权限时，写入和读取都要以后端裁剪为准。
- 涉及菜单权限时，必须把“入口权限”和“数据范围权限”分开实现和验证。

### 隐藏界面与二级入口覆盖清单

每个功能交付前必须检查主页面之外的真实操作入口：

- 主入口：一级菜单、二级 tab、页面按钮、表格行操作。
- 隐藏界面：新增弹窗、编辑弹窗、详情弹窗/抽屉、审核弹窗、付款弹窗、上传弹窗、凭证/图片/标签预览、批量操作面板、确认框、无权限提示。
- 字段：是否来自文本需求或 Excel 字段，是否已有接口字段可复用，是否已有数据库字段可复用，是否需要角色裁剪，是否涉及日志。
- 状态：提交前状态、提交后状态、失败后状态、刷新位置、是否保留筛选条件。
- 权限：仓库不能看价格、利润、应付、付款信息；业务员不能看真实应付、真实代理渠道；财务只看职责范围内数据；管理员可见敏感字段也必须有日志追溯。
- 行为：标题要表达当前动作，主按钮文案要匹配后端动作，取消/关闭不能造成状态混乱，成功后要明确关闭弹窗、刷新列表或保留当前筛选。

## Frontend Layout Guardrails

- `frontend-design` 是新建/重塑前端功能的默认设计门槛：开工前先明确页面服务的岗位、单一业务任务、核心字段、主操作、空/错/加载状态，以及一处与物流/财务/仓库场景相关且不影响效率的视觉或交互记忆点。
- Sunny 后台页面的设计目标是“真实业务高效处理”，不是营销站视觉。财务、仓库、订单、客服、市场等高频页面必须优先保证可扫读、可比较、少滚动、字段完整、权限状态清楚。
- `frontend-design` 的字体、配色、结构和动效建议必须服从现有设计系统、AntD 组件、业务字段、权限裁剪、审计和测试；不得为了视觉特色新增无业务价值的依赖、抽象或装饰。
- `frontend-design` 不只看一级页面。只要用户能看到、点击、提交，或会影响业务状态，弹窗、抽屉、表格行操作、批量操作、上传、预览、字段设置、确认框、二级/三级入口和空/错/加载/无权限/禁用状态都必须一起检查。
- 不允许把 4 列以上的数据表格塞进窄卡片或三列卡片网格；必须使用全宽区块、页签、折叠区或明确的横向滚动。
- 后台表格必须定义关键列宽和 `scroll.x`，操作列不能被裁切，中文列名和字段值不能被挤成竖排。
- 表格操作按钮使用稳定的横向排布；如果空间不足，优先让表格横向滚动，而不是压缩字段内容。
- 财务、仓库、订单等高频工作页以“可扫读、可比较、少滚动”为优先，不为了卡片对称牺牲表格可读性。
- 功能标题、二级目录或卡片标题已经说明用途时，不再额外放大块说明 Alert。
- KPI/统计卡与主操作区之间保持紧凑，通常为 12-16px；禁止出现没有内容承载的大面积空白。
- 页面文案避免出现开发阶段词汇，例如 `mock`、`M3`、`已接入后端`、`最小闭环`。
- 筛选区、资料库、费用表等高频组件必须使用“字段清楚、按钮靠近动作、行高稳定、分页明确”的排版。
- 前端修改后通过响应式规则检查、组件测试、类型检查和生产构建覆盖 1366px 与宽屏布局边界；实际字段、按钮、表头是否覆盖、重影、竖排或裁切由用户在 47 页面人工确认。

### 弹窗/抽屉/隐藏界面设计规则

- 业务类弹窗优先按基础信息、业务数据、费用数据、附件/凭证、审核记录、操作日志分区，不堆字段。
- 财务类弹窗必须突出应收、应付、已付、未付、差额、汇率、币种、凭证、到账时间、付款时间和代理账单来源。
- 仓库类弹窗必须突出客户编号、包裹号、入库标签、重量、尺寸、件数、库位、理货状态和排货状态，不展示价格相关字段。
- 业务/客服类弹窗必须突出运单号、转单号、渠道、状态、问题件、预计到港和签收确认，敏感代理成本字段默认隐藏。
- 确认类弹窗必须写清将改变什么状态、是否可撤回、是否影响财务/仓库/客服/代理账单；危险动作不能只写“确定吗”。
- 弹窗宽度不能挤压字段，表单标签不能竖排或截断，表格列不能遮挡关键操作，底部按钮位置要稳定，窄屏至少不能遮挡提交按钮和关键字段。

### UI 重构发布与人工视觉验收规则

- 已落地模块可以做 UI 重构，但每次优先按模块或业务闭环拆小，例如仓库、订单/业务、客服、财务、基础资料、权限/设置。
- 一轮重构只处理一个模块或一个闭环，并同时覆盖该模块的大页面和相关隐藏界面。
- UI 重构完成本地代码验证后，直接按 `docs/47-cloud-docker-release.md` 精确发布到 47；不等待本地或线上浏览器自动验收。
- UI 重构不得默认改变业务口径、数据库结构、线上数据、权限模型或接口契约；必须补接口、字段或后端逻辑时，单独列为后端改动。
- 重构完成后至少用组件测试或定向页面测试覆盖入口、弹窗、表单和关键交互，用 API/权限测试覆盖角色字段与写入边界，并通过相关类型检查或生产构建。
- 发布后检查 47 源码 checksum、静态产物标记、公网/容器健康、相关 API 和最近错误日志；页面排版、遮挡、颜色、密度和响应式由用户人工验收。
- 常规 Web/API 代码发布已获持续授权；破坏性迁移、真实付款、批量生产数据写入或不可逆数据清洗仍须用户确认。

### 无浏览器验收与 47 验证流程

验证码和浏览器点击耗时高且不稳定，本地数据也不保证与 47 一致，因此本地页面通过不能作为线上业务事实的主要证据。Codex 后续不操作浏览器、不做验证码登录、Session 注入或自动截图。UI 设计和视觉效果由用户在 47 页面人工验收；Codex 负责代码、接口、构建、发布与线上服务证据。

当前可执行流程：

1. 完成代码修改，只运行能阻止明显错误上线的最小安全门：`git diff --check`，再选择一个最相关的单元/组件/API 测试、类型检查或必要审查；47 必然生产构建时不在本地重复构建。
2. 按候选文件白名单精确发布到 47，只构建和重启受影响服务；Prisma 没有变化时不得运行迁移。
3. 发布后依次检查容器状态、公网/容器 health、目标 API、线上源码 checksum 或静态产物标记、最近错误日志。
4. 鉴权接口使用 47 容器内短期 JWT、服务端本地接口或只读数据库查询，不请求图片验证码，不依赖浏览器会话；权限场景至少验证允许路径和一个拒绝路径。
5. 线上写接口只使用安全、可回滚的固定样本，并核对持久化结果和审计日志；可能污染真实财务、订单、仓库或客户数据时改用只读证据或先向用户确认样本。
6. 线上验证失败时立即定位根因、修改代码、执行最小相关本地验证、重新精确发布并复验；不退回浏览器或验证码链路，不把已知失败留给用户发现。
7. 线上证据通过后一次性汇报发布结果，以及用户需要人工检查的页面路径、操作入口和视觉点；用户反馈作为下一轮 UI 调整输入。

中断恢复规则：出现 `stream disconnected`、工具中断或用户说“继续执行 / 继续完成”后，必须先重新读取当前 `AGENTS.md`、`git status --short` 和本任务状态文件，再继续动作。旧状态文件中的“仅本地完成”“等待截图”不能覆盖当前总规则；运行时代码没有实际尝试发布，不得标记完成。

禁止方案：

- 本地全局关闭鉴权或修改 `RbacGuard` 放行。
- 使用匿名管理员、伪造权限数组或只在前端隐藏字段。
- 把 47 token 或 `JWT_SECRET` 复制到本地浏览器。
- 把 token 放进查询参数、`VITE_*` 变量、终端日志或可持久化测试报告。
- 为了验收在本地或 47 反复请求验证码、登录或操作浏览器；鉴权接口只使用不输出密钥的服务端验证方式。

## Commands And Verification

常用命令：

```bash
npm run dev
npm run dev:api
npm run build
npm run test:shared:safe -- --run <测试文件或模式>
npm run test:api:safe -- --run <测试文件或模式> -t <用例名>
npm run test:web:safe -- --run <测试文件或模式> -t <用例名>
npm run test:all:safe
npm run lint
npm run typecheck
npm run governance:check
npm run sync:47
```

验证优先级：

1. 修改共享领域逻辑时，优先跑 `npm run test:shared:safe -- --run <测试文件或模式>`。
2. 修改 API 时，优先跑 `npm run test:api:safe -- --run <测试文件或模式> -t <用例名>`、类型检查或局部请求验证。
3. 修改前端时，优先跑 `npm run test:web:safe -- --run <测试文件或模式> -t <用例名>`、对应类型检查或生产构建；发布后验证 47 静态产物、接口和日志，视觉效果交由用户人工检查。
4. 跨模块且确实需要完整回归时，再运行 `npm run test:all:safe`、`npm run typecheck` 或 `npm run build`。
5. 修改 Agent、测试安全入口或发布规则时，运行 `npm run governance:check`；Shell 发布脚本另执行 `bash -n`。

快速验证入口：

- Shared 定向测试：`npm run test:shared:safe -- --run <测试文件或模式>`
- Web 分域集成测试：`npm run test:web:safe -- --run <模块测试文件或模式>`
- API e2e 测试：`npm run test:api:safe -- --run <e2e 测试文件或模式>`
- 完整安全回归：`npm run test:all:safe`
