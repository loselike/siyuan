# Sunny 开发会话详细规则

本文档承接 `AGENTS.md` 中不适合每次默认展开的细则。需要做多会话协作、长需求拆卡、模块大改、前端布局治理或验证策略时读取本文档。

## 多会话协作

会话按以下优先级分工，避免多个会话同时改共享文件：

1. 主会话：维护 `.codex-state.md`、合并结论、推进主任务卡。
2. 发布会话：只负责 47 同步、Docker 发布、迁移和健康检查；不顺手改业务代码。
3. 业务模块会话：一次只负责一个明确模块，例如仓库、订单、财务、权限、基础资料。
4. UI 调试会话：只输出截图、图片、交互结论和验收问题；不改代码。
5. UI 落地会话：根据 UI 调试会话输出做前端落地；能复用就复用，系统确实没有能力时才补接口或逻辑。

共享高风险文件包括 `.codex-state.md`、Prisma schema/migrations、RBAC、`packages/shared`、全局样式、共享表格组件、`App.tsx`、包管理文件和发布脚本。改这些文件前必须说明影响面，并确认没有其他会话正在处理同一区域。

## Ponytail Development Discipline

本项目默认采用 Ponytail 风格作为常驻开发纪律：少写代码、少加依赖、少造抽象，优先交付最小正确闭环。该纪律用于控制复杂度，不能覆盖安全、权限、财务一致性、数据完整性、测试验证和用户明确需求。

- 先复用现有模块、类型、API、样式和测试，再考虑新增文件或新抽象。
- 优先使用 TypeScript/Node/浏览器平台能力和仓库已有依赖；新增依赖前必须说明为什么现有能力不足。
- 每次改动尽量靠近需求涉及的模块；禁止顺手重构无关代码、批量格式化无关文件或改动无关业务流程。
- 新抽象只有在减少真实重复、降低共享复杂度或符合现有模块边界时才允许添加。
- 能删掉旧分支、旧 fallback、重复 UI、重复映射或无用 helper 时，优先删除；但删除前必须确认没有测试、路由、页面或线上兼容依赖。
- 对临时简化方案，用 `ponytail:` 注释写明边界和后续触发条件。

## 最低修改与复用优先规则

每次开发前先做复用检查，避免为了新入口重复造接口、重复造组件或复制业务逻辑：

- 是否已有相同业务入口，或已有页面、弹窗、抽屉、详情面板可以扩展。
- 是否已有 API、DTO、查询参数、状态字段或共享类型可以承载本次需求。
- 是否已有数据库字段或持久化位置可以表达该业务含义。
- 是否已有权限判断、字段裁剪、菜单入口、数据范围和操作日志可以复用。
- 是否已有测试样本、测试桩或验收命令可以扩展。

开发顺序固定为：

1. 先复用现有 UI 入口。
2. 再补齐现有组件字段和状态。
3. 再复用现有接口返回必要字段。
4. 再补接口参数或响应裁剪。
5. 最后才新增接口、数据库字段或新组件。

禁止做法：

- 没检查现有接口就新增接口。
- 没检查现有组件就新建重复弹窗。
- 为一个页面复制一套相似后端查询。
- 前端隐藏敏感字段但后端仍返回全量敏感数据。
- UI 重构时顺手改变业务流转、权限模型、数据库结构或线上数据。
- 未经用户确认直接发布 UI 重构到 47。

只有满足以下条件之一，才允许新增接口、字段、组件或后端逻辑：

- 文本需求或 Excel 字段存在真实业务字段，当前能力没有承载位置。
- 当前接口无法保证敏感字段以后端方式裁剪。
- 当前状态流转缺失，复用会造成错误业务闭环。
- 当前日志无法追溯审核、反审、付款、作废、转单号、出库等关键动作。
- 当前组件无法表达必要业务结构，例如多费用行、水单匹配、标签预览或代理账单核对。
- 复用会造成越权、财务口径错误、重复提交或数据追溯断裂。

处理既有代码时：

- 普通功能开发不触发旧代码审计；只按本次需求做最小相关改动。
- 只有用户明确要求重构、瘦身、整理旧代码、降低复杂度，或当前文件继续堆叠会明显增加风险时，才先审计再改动。
- 审计时先列出重复、过度封装、无用依赖、大文件堆积和可合并逻辑，不一次性全项目重构。
- 业务大文件拆分只沿现有领域边界推进，例如 finance、warehouse、orders、routing；禁止为了“看起来更架构化”新增无业务价值的层。

## Long Requirement Protocol

用户贴长 PRD、截图拆解、阶段计划或详细字段清单时，不要把整份文档当成一次性实现范围。先压缩成一张短执行卡片：

```md
目标：
本次阶段：
涉及模块：
必须做：
不要做：
验收标准：
最小验证：
```

处理规则：

- 如果文档包含多阶段计划，默认只执行第一阶段或用户明确指定的阶段。
- 只读取与本次阶段相关的代码；不要因为文档同时提到 API、数据库、权限、UI、发布就全部展开。
- 每次实现必须控制在一个可验证闭环，优先复用现有接口、类型、测试和页面结构。
- 大功能优先落地“展示/读取”或“单类 CRUD”，再做批量操作、权限矩阵、列设置、通知、导入导出等增强。
- 同一轮不要同时做多阶段功能、47 发布、巨型模块重构、数据库大迁移；除非用户明确要求。

## Product Priorities

- 财务资料库必须支持真实增删改查，不做静态假页面。
- RMB 统一、币种自动识别、结算方式和费用计算属于跨前后端与数据库的核心能力。
- 订单、客户、财务、仓储、权限相关改动要保持 API、前端状态、数据库字段一致。
- 业务动作尽量可追溯，涉及财务和权限的变更要考虑审计。

## Module Delivery Checklist

新增或大改业务模块时，默认按这张清单交付：

- 先确定模块边界：前端放对应 `apps/web/src/modules/<domain>`，API 放 `apps/api/src/modules`，共享类型放 `packages/shared`；禁止重新把页面逻辑堆回 `App.tsx`。
- 新建前端模块、二级功能、工作台、表单、详情、看板或明显重塑已有页面时，必须读取并遵循 `.agents/skills/frontend-design/SKILL.md`；弹窗、抽屉、行内操作、上传、预览、确认框、字段设置、二级/三级入口和空/错/加载/无权限/禁用状态也属于同一轮设计与验收范围；小型 bugfix、文案修正、字段补显隐或测试修复可复用现有设计，不强制重新做完整设计方案。
- 后端新功能必须优先落在领域子模块里。Controller 只做路由/权限/输入输出，Service 做业务规则，Repository 做持久化。
- API 测试默认按领域拆分，例如 `app.finance.e2e.test.ts`、`app.warehouse.e2e.test.ts`、`app.orders.e2e.test.ts`、`app.pricing.e2e.test.ts`。
- 需求字段必须做“前端表单/展示、共享类型、Prisma 字段或持久化位置、API 输入输出、测试数据”五点对应；暂不落地的字段必须写明原因和后续阶段。
- 后端必须成为业务事实来源；新增字段不能只停留在前端状态或测试桩，跨模块数据要能被后续流程读取。
- 开发前必须把 PRD 字段拆成验收矩阵，逐项标记“已落地 / 已映射 / 延期”。
- 每个新模块交付前必须输出简短“需求落地核对”：已落地字段、已落地流程、后端互通点、延期项和原因。
- 新状态或流程节点必须同时补共享状态、后端状态流转、前端筛选/展示、日志记录和回归测试。
- 涉及审核、反审核、撤销、反核销的模块，必须检查下游流转状态，不能直接回退已付款、已核销、已归档等状态。
- 导出必须按当前完整筛选条件或勾选范围输出，不能只导当前分页或固定前 100 条；后端仍要按权限裁剪字段。
- 上传、粘贴、凭证、水单等入口不能只做视觉按钮；暂未接对象存储时，必须明确保存文件元数据和 URL/路径。
- 列表到详情类页面禁止默认选中第一条数据，除非需求明确要求。
- 前端测试桩必须 mock 新增的真实 API 路径，不允许只依赖本地备用数组或旧接口让测试“看起来能过”。
- 聚合提交接口要在后端事务里完成主表、明细、费用、仓库包裹、审计日志等同步写入；草稿和正式提交的副作用必须分开。
- 涉及角色权限时，写入和读取都要以后端裁剪为准。
- 涉及菜单权限时，必须把“入口权限”和“数据范围权限”分开实现和验证。

### 隐藏界面与二级入口覆盖清单

每个功能交付前必须检查主页面之外的真实操作入口：

- 主入口：一级菜单、二级 tab、页面按钮、表格行操作。
- 隐藏界面：新增弹窗、编辑弹窗、详情弹窗/抽屉、审核弹窗、付款弹窗、上传弹窗、凭证/图片/标签预览、批量操作面板、确认框、无权限提示。
- 字段：是否来自文本需求或 Excel 字段，是否已有接口字段可复用，是否已有数据库字段可复用，是否需要角色裁剪，是否涉及日志。
- 状态：提交前状态、提交后状态、失败后状态、刷新位置、是否保留筛选条件。
- 权限：仓库不能看价格、利润、应付、付款信息；业务员不能看真实应付、真实代理渠道；财务只看职责范围内数据；管理员可见敏感字段也必须有日志追溯。
- 行为：标题要表达当前动作，主按钮文案要匹配后端动作，取消/关闭不能造成状态混乱，成功后要明确关闭弹窗、刷新列表或保留当前筛选。

## Frontend Layout Guardrails

- `frontend-design` 是新建/重塑前端功能的默认设计门槛：开工前先明确页面服务的岗位、单一业务任务、核心字段、主操作、空/错/加载状态，以及一处与物流/财务/仓库场景相关且不影响效率的视觉或交互记忆点。
- Sunny 后台页面的设计目标是“真实业务高效处理”，不是营销站视觉。财务、仓库、订单、客服、市场等高频页面必须优先保证可扫读、可比较、少滚动、字段完整、权限状态清楚。
- `frontend-design` 的字体、配色、结构和动效建议必须服从现有设计系统、AntD 组件、业务字段、权限裁剪、审计和测试；不得为了视觉特色新增无业务价值的依赖、抽象或装饰。
- `frontend-design` 不只看一级页面。只要用户能看到、点击、提交，或会影响业务状态，弹窗、抽屉、表格行操作、批量操作、上传、预览、字段设置、确认框、二级/三级入口和空/错/加载/无权限/禁用状态都必须一起检查。
- 不允许把 4 列以上的数据表格塞进窄卡片或三列卡片网格；必须使用全宽区块、页签、折叠区或明确的横向滚动。
- 后台表格必须定义关键列宽和 `scroll.x`，操作列不能被裁切，中文列名和字段值不能被挤成竖排。
- 表格操作按钮使用稳定的横向排布；如果空间不足，优先让表格横向滚动，而不是压缩字段内容。
- 财务、仓库、订单等高频工作页以“可扫读、可比较、少滚动”为优先，不为了卡片对称牺牲表格可读性。
- 功能标题、二级目录或卡片标题已经说明用途时，不再额外放大块说明 Alert。
- KPI/统计卡与主操作区之间保持紧凑，通常为 12-16px；禁止出现没有内容承载的大面积空白。
- 页面文案避免出现开发阶段词汇，例如 `mock`、`M3`、`已接入后端`、`最小闭环`。
- 筛选区、资料库、费用表等高频组件必须使用“字段清楚、按钮靠近动作、行高稳定、分页明确”的排版。
- 前端修改后至少检查 1366px 与宽屏两类视口，确认字段、按钮、表头没有覆盖、重影、竖排或裁切。

### 弹窗/抽屉/隐藏界面设计规则

- 业务类弹窗优先按基础信息、业务数据、费用数据、附件/凭证、审核记录、操作日志分区，不堆字段。
- 财务类弹窗必须突出应收、应付、已付、未付、差额、汇率、币种、凭证、到账时间、付款时间和代理账单来源。
- 仓库类弹窗必须突出客户编号、包裹号、入库标签、重量、尺寸、件数、库位、理货状态和排货状态，不展示价格相关字段。
- 业务/客服类弹窗必须突出运单号、转单号、渠道、状态、问题件、预计到港和签收确认，敏感代理成本字段默认隐藏。
- 确认类弹窗必须写清将改变什么状态、是否可撤回、是否影响财务/仓库/客服/代理账单；危险动作不能只写“确定吗”。
- 弹窗宽度不能挤压字段，表单标签不能竖排或截断，表格列不能遮挡关键操作，底部按钮位置要稳定，窄屏至少不能遮挡提交按钮和关键字段。

### UI 重构本地先行规则

- 已落地模块可以做 UI 重构，但每次优先按模块或业务闭环拆小，例如仓库、订单/业务、客服、财务、基础资料、权限/设置。
- 一轮重构只处理一个模块或一个闭环，并同时覆盖该模块的大页面和相关隐藏界面。
- UI 重构默认只落本地，不自动发布到 47；用户本地检查通过后，才按 `docs/47-cloud-docker-release.md` 进入 47 发布流程。
- UI 重构不得默认改变业务口径、数据库结构、线上数据、权限模型或接口契约；必须补接口、字段或后端逻辑时，单独列为后端改动。
- 重构完成后至少验证页面能打开、弹窗能打开、表单能输入、关键按钮不遮挡、角色字段不越权，以及相关构建或测试通过。
- 未经用户确认，不执行 47 发布、不迁移线上数据库、不清洗线上数据。

## Commands And Verification

常用命令：

```bash
npm run dev
npm run dev:api
npm run build
npm test
npm run test:web
npm run test:api
npm run lint
npm run typecheck
npm run sync:47
```

验证优先级：

1. 修改共享领域逻辑时，优先跑 `npm run test -w @siyuan/shared`
2. 修改 API 时，优先跑 API 相关测试、类型检查或局部请求验证
3. 修改前端时，优先跑 Web 测试，并启动页面做浏览器验证
4. 跨模块改动后，再跑根目录 `npm test`、`npm run typecheck` 或 `npm run build`

快速验证入口：

- Web 分域集成测试：`npm run test:web`
- API e2e 测试：`npm run test:api`
- 47 同步预演：`npm run sync:47`
- 47 真实同步：`npm run sync:47 -- --apply`
