## 3. 总体开发策略

推荐路线：先做“可运营的履约闭环”，再补报价财务，最后做承运商/API 深水区。

理由：

- 当前仓库已有运单状态池与运营工作台，最适合先承接员工端“操作”文档中的预报、收货、排货、打单、发货、轨迹、问题件链路。
- 报价和财务文档数量多、规则复杂，若过早做全量算法会拖慢 MVP；应先做可配置的规则框架和少量代表性规则。
- API/承运商对接文档非常多，且每家差异明显，第一阶段应通过“集成适配器接口 + 模拟适配器”确定边界，避免硬编码 DHL/FedEx/华磊/哲盟细节。

目标：把抓取结果变成开发可追溯资料，不让需求来源散落。

交付：

- 保留 `scraped_docs/itdida_support/README.md` 作为人工索引。
- 保留 `all_docs.json` 作为机器可检索数据。
- 增加一个轻量查询脚本或 npm script，用关键词查询文档 ID、标题、路径、媒体数量。

验收：

- 输入 `报价`、`转单`、`应收财务`、`问题件` 等关键词可列出对应文档。
- 任意开发任务必须引用至少一个本地文档路径或文档 ID。

### M3：报价、查价与计费规则

证据：

- 员工端报价组文档 ID `167` 有 30 个子功能。
- 员工端查价组文档 ID `168` 有 4 个子功能。
- 常见问题中 `报价` 命中 146 篇，`附加费` 38 篇，`分区` 24 篇。
- 代表性规则文档包括文档 ID `4502`、`4051`、`4086`。

开发范围：

- 报价模型：客户报价、代理成本价、承运商价、销售成本价。
- 分区：国家/邮编/偏远分区。
- 燃油率。
- 附加费：固定金额、按重量、按国家、按公式条件。
- 计费重：实重、材积重、取大、单件/整票进位。
- 查价：员工端查客户/代理/销售/承运商价，客户端查可用价格。

策略：

- 第一版不要硬编码所有历史算法，先做规则引擎最小能力：条件、公式、阶梯、进位、取大。
- 从抓取文档挑 5 条代表性规则做回归测试：
  - DHL 单件 30KG 上下进位规则。
  - 方数与 KG 同报价参与计算。
  - 日本专线三边和与重量取大。
  - 超长/超重/围长附加费。
  - 偏远附加费按国家/邮编/地址类型。

验收：

- 同一运单可输出应收价、代理成本、毛利。
- 报价变更有版本，不影响历史已出账费用。
- 客户端只看到授权渠道和客户报价。

### M8：AI 助手

证据：

- 当前 README 已把 AI 辅助能力列入项目方向。
- 当前 `packages/shared/src/index.ts` 已有 `createShipmentInsights`、`createAutomationPlan`、`createFulfillmentAdvice` 等雏形。
- 文档中大量 FAQ 是排查类知识，适合做检索增强而非让模型自由发挥。

开发范围：

- 文档检索：基于本地抓取 Markdown/JSON 建索引。
- 运单异常解释：只基于运单事件、轨迹、费用、问题件。
- 客户回复草稿。
- 报价解释。
- 今日待办摘要。

防幻觉边界：

- AI 输出必须附引用：文档 ID、本地 Markdown 路径、业务对象 ID。
- 无引用时只能回答“资料不足，需要人工确认”。
- AI 不直接执行财务核销、关闭问题件、删除运单、推送承运商等高风险动作。

验收：

- 对“DHL 电池金句显示不了”“轨迹超过 3 天没更新”“客户余额不足预报限制”等问题，AI 回答能引用本地文档。
- AI 建议保存审计记录。

## 7. 测试策略

- 领域层：状态迁移、计费重、报价规则、附加费公式、财务核销。
- API 层：权限、租户/客户隔离、状态迁移拒绝、导入校验。
- 前端：工作台筛选、批量操作可用性、客户门户隔离。
- 集成：模拟适配器查价/打单/轨迹。
- AI：必须校验回答带引用；无证据时拒答。

## 8. 明确不在第一阶段做

- 不复刻旧系统界面，只学习业务闭环。
- 不一次性实现 162 篇 API/承运商对接。
- 不让 AI 自动执行高风险动作。
- 不先做完整财务复杂场景，如跨币种抵扣、多账期模板全覆盖。
- 不把常见问题里的单个客户定制规则直接硬编码进核心逻辑，先沉淀为可配置规则。

## 9. 下一步建议

第一张开发计划应选择 M1 + M2 的最小闭环：

1. Prisma 数据模型与种子数据。
2. 运单真实 API 替换内存数据。
3. 运单创建、导入、收货、排货、发货、轨迹事件。
4. 问题件最小能力。
5. 客户端预报进入员工端队列。

这能最快验证系统主干，并为报价、财务、承运商对接留下稳定扩展点。
